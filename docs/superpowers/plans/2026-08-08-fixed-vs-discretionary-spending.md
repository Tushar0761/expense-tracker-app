# Fixed vs Discretionary Expense Analysis Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the dashboard split spending into Fixed (EMI, rent, subscriptions) vs Discretionary (everything else) via a category-level tag with per-expense override, so loan EMI stops dominating every chart/KPI, and add a simple discretionary-budget burn-down.

**Architecture:** A new `spend_type` enum lives on `category_master` (default classification) and nullable on `expenses_data_master` (override; `null` = inherit from category). All expense-aggregation queries (`dashboard`, `summary`, `category-totals`, plain list) gain an optional `spendTypeFilter` query param that filters by the *effective* type (`expense.spendType ?? category.spendType`). The frontend adds a 3-way toggle (All / Discretionary / Fixed) on the Dashboard page that drives every dashboard data fetch, plus a minimal single-row budget model/endpoint and a burn-down card. Category and expense edit UIs gain a spendType control; Refine Expenses gains it as a bulk-edit field.

**Tech Stack:** NestJS + Prisma (MySQL) backend, React + TypeScript + Vite frontend, TanStack Query, react-hook-form + zod, shadcn/ui + Tailwind.

## Global Constraints

- Backend `ValidationPipe` uses `whitelist: true` + `transform: true` (see `backend/src/main.ts`) — every new DTO field needs an explicit `class-validator` decorator or it will be silently stripped.
- All API routes are prefixed `/api` globally — do not include `/api` in controller `@Controller()` paths (matches existing pattern).
- No automated test suite exists in this repo. Verification is manual: exercise endpoints directly and confirm behavior in the running dev app (see spec's "Testing approach").
- Single-user, no-auth app — no per-user scoping needed anywhere in this feature.
- Follow existing file conventions exactly: DTOs in `<module>.dto.ts`, one service/controller per module, Prisma singleton via `PrismaService` (except `accounts` module, which instantiates `PrismaClient` directly — do not copy that inconsistency into new code; use `PrismaService` like `expenses`/`categories` do).

- [ ] **Step 2: Build a shared Prisma `where` fragment for the spend-type filter**

Because `getDashboardKPIs`/`getExpenseSummary`/`getCategoryWiseTotals` currently fetch rows via `findMany`/`aggregate` without a `category_master` join filter, the cleanest way to filter by *effective* type (which depends on both `expense.spendType` and its category's default) in a single Prisma `where` clause is:

```typescript
function buildSpendTypeWhere(
  filter: SpendTypeFilter | undefined,
): Prisma.expenses_data_masterWhereInput {
  if (!filter || filter === 'ALL') return {};
  if (filter === 'FIXED') {
    return {
      OR: [
        { spendType: 'FIXED' },
        { spendType: null, category_master: { spendType: 'FIXED' } },
      ],
    };
  }
  // DISCRETIONARY
  return {
    OR: [
      { spendType: 'DISCRETIONARY' },
      { spendType: null, category_master: { spendType: 'DISCRETIONARY' } },
    ],
  };
}
```

Add this as a private method on `ExpensesService` (or a top-level function in the same file, consistent with `getPeriodKey` being a private method — private method is more consistent with existing style):

```typescript
  private buildSpendTypeWhere(

        OR: [
```

Then apply `buildSpendTypeWhere` to all three aggregate `where` clauses (`thisPeriod`, `lastPeriod`, `overall`) and to the `recentTransactions` `findMany`. Since each of those currently has a distinct `where` shape (`dateFilter` or `{ date: { gte: thisMonthStart } }` for `thisPeriod`; `comparisonDateFilter` for `lastPeriod`; `{}` implicit for `overall`; no `where` at all for `recent`), the simplest correct approach is to combine each with `AND`:

```typescript
    const spendTypeWhere = this.buildSpendTypeWhere(spendTypeFilter);
    const withSpendType = (
      base: Prisma.expenses_data_masterWhereInput | undefined,
    ): Prisma.expenses_data_masterWhereInput =>
      spendTypeWhere.OR ? { AND: [base ?? {}, spendTypeWhere] } : (base ?? {});

    const [thisPeriod, lastPeriod, overall, recent, accounts] =
      await Promise.all([
        this.prisma.expenses_data_master.aggregate({
          where: withSpendType(dateFilter ? dateFilter : { date: { gte: thisMonthStart } }),
          _sum: { amount: true },
          _count: true,
        }),
        this.prisma.expenses_data_master.aggregate({
          where: withSpendType(comparisonDateFilter),
          _sum: { amount: true },
          _count: true,
        }),
        this.prisma.expenses_data_master.aggregate({
          where: withSpendType(undefined),
          _sum: { amount: true },
          _count: true,
        }),
        this.prisma.expenses_data_master.findMany({
          where: withSpendType(undefined),
          orderBy: { date: 'desc' },
          take: 10,
          include: {
            category_master: true,
          },
        }),
        this.prisma.account_master.findMany(),
      ]);
```

Note: `lastPeriod`'s `where: comparisonDateFilter` was previously passed even when `comparisonDateFilter` is `undefined` (Prisma treats `where: undefined` as "no filter", i.e. same as `{}` — the `withSpendType` helper's `base ?? {}` preserves that behavior exactly).

```typescript
import { Injectable } from '@nestjs/common';
import { PrismaService } from 'src/prisma/prisma.service';
import { UpsertBudgetDto } from './budget.dto';

@Injectable()
export class BudgetService {
  constructor(private prisma: PrismaService) {}

  async get() {
    return this.prisma.budget_setting.findFirst({
      orderBy: { id: 'asc' },
    });
  }

  async upsert(dto: UpsertBudgetDto) {
    const existing = await this.prisma.budget_setting.findFirst({
      orderBy: { id: 'asc' },
    });

    if (existing) {
      return this.prisma.budget_setting.update({
        where: { id: existing.id },
        data: { discretionaryBudget: dto.discretionaryBudget },
      });
    }

    return this.prisma.budget_setting.create({
      data: { discretionaryBudget: dto.discretionaryBudget },
    });
  }
}
```

(A single-row table has no natural unique key to upsert on cleanly with Prisma's `upsert()`, so this is a plain find-then-create-or-update — simpler than fabricating a fixed `id: 1` convention.)
